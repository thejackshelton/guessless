## Question 2

**Does `encodeSlot` in `src/value.ts` mutate its `records` parameter?**

### Answer: YES.

`encodeSlot` is declared at `src/value.ts:146-152` with the parameter `records: SerializedRecord[]` (line 150) — a mutable array type, not `ReadonlyArray`. Mutating it is in fact the function's primary output channel: it returns only a `SerializedSlot` reference (`{ $ref: id }`), and the actual serialized record graph is accumulated by pushing into `records`. The caller `serializeGraphValue` (line 122) creates the array at line 125, passes it in at line 127, and reads the mutated result out at line 140.

### Mutation sites — direct `records.push(...)`

- `src/value.ts:176` — pushes the `date` record
- `src/value.ts:185` — pushes the `regexp` record
- `src/value.ts:194` — pushes the `url` record
- `src/value.ts:204` — pushes the `array-buffer` record
- `src/value.ts:219` — pushes the `typed-array` record
- `src/value.ts:235` — pushes the `data-view` record
- `src/value.ts:257` — pushes the `array` record
- `src/value.ts:274` — pushes the `map` record
- `src/value.ts:308` — pushes the `set` record
- `src/value.ts:328` — pushes the plain-`object` record

### Mutation sites — in-place mutation of objects already inside `records`

For the four container kinds, the record is pushed into `records` **first** (so its `id` is reserved before recursion, which is how cycles resolve), then its child collection is filled afterwards through a cast that strips the declared `readonly`. These mutate the contents of the array the caller holds:

- `src/value.ts:258` — `(record.items as SerializedSlot[]).push(...)` on the record pushed at 257
- `src/value.ts:292` — `(record.entries as Array<readonly [SerializedSlot, SerializedSlot]>).push(...)` on the record pushed at 274
- `src/value.ts:312` — `(record.values as SerializedSlot[]).push(slot)` on the record pushed at 308
- `src/value.ts:333` — `(record.fields as Array<readonly [string, SerializedSlot]>).push([key, slot])` on the record pushed at 328

### Indirect mutation — the same array reached through recursion

These pass the same `records` reference onward; the mutation lands at the sites above, but they are the call edges that make it happen and they are why "does it mutate" cannot be answered by looking at one branch:

- `src/value.ts:261, 277, 284, 311, 331` — recursive `encodeSlot(..., records, diagnostics)` calls for array items, map keys, map values, set values, and object fields.
- `src/value.ts:223, 238` — `encodeArrayBufferViewBuffer(value, path, seen, records, diagnostics)`, which forwards `records` (parameter declared at `src/value.ts:364`) into `encodeSlot` at `src/value.ts:373`.

### Non-mutating uses, for contrast

`src/value.ts:174, 183, 192, 202, 217, 233, 248` are all `const id = records.length` — reads of the array length used to allocate the next record id. There is no reassignment of `records` and no aliasing of it to another binding anywhere in the file.

Note on the declared type: the public payload type declares `records: ReadonlyArray<SerializedRecord>` (`src/value.ts:92`), so the mutability is internal to construction — the array is mutated freely while building, then handed out behind a readonly type at line 140. The `readonly` in the type therefore does not contradict the answer.

The list covers every mutation of the `records` parameter and of objects reachable inside it, within `src/value.ts`.

### How this was established

`encodeSlot` and its `records` parameter were traced by reading the full function body (`src/value.ts:146-338`) plus its helper `encodeArrayBufferViewBuffer` (`src/value.ts:360-374`) and its caller `serializeGraphValue` (`src/value.ts:122-144`) — the whole reachable set, not a sample. The site list was then closed mechanically rather than by eye: `grep -n "records\." src/value.ts` enumerates every member access on the parameter and shows the set is exactly `.push` and `.length` with nothing else; `grep -n "= records\|records ="` confirms no reassignment and no alias, which is what makes the enumeration exhaustive. A separate grep for `record.items|record.entries|record.values|record.fields` caught the post-push in-place mutations that a `records.`-only search would have missed, since those write through a `record` binding rather than through the array.
